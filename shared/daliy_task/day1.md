# TapLens 第一天工作具体安排

> 适用成员：A（Flutter APP）、B（后端与云端）、C（Android 本地安全）、D（AI 与测试）  
> 工作方式：每个人上线时间可以不同，按任务顺序推进，不要求同时在线。

## 第一天到底要完成什么

第一天的目标是：**四个人各自搭好可以继续开发的工程骨架，约定数据怎么传，并让手机 APP 展示一份固定报告。**

这里的“固定报告”是提前写好的演示数据，目的是先证明页面和数据格式能接起来。第一天不要求真实扫码、真实网页沙箱或真实 AI 分析。

当天最重要的共同交付物是四份数据契约（每份包含 Schema 和一个 example）：

| 数据文件 | 负责人 | 用大白话解释 |
|---|---|---|
| `analysis-input` | A | 用户交给 APP 的是什么：链接、二维码内容、海报文字等 |
| `local-evidence` | C | 手机本地查到了什么：目标包名、网页跳转、表单等 |
| `cloud-evidence` | B | 云端浏览器查到了什么：跳转链、请求、页面字段等 |
| `analysis-report` | D | 最后给用户看的结论、差异和证据编号 |

A 同时维护 `common.schema.json`，统一风险等级、时间格式、任务 ID、证据编号等公共写法；B、C、D 一起确认。正式文件放在 `shared/contracts/`。**聊天里说定的字段不算正式接口，以仓库中的 Schema 和 example 为准。**

## 上线后统一按这个顺序

1. 拉取最新代码，阅读根目录 `README.md`、`shared/README.md` 和 `shared/PREPARATION_CHECKLIST.md`。
2. 看自己负责的契约草稿；没有草稿就先建一个最小版本，并告诉其他三人文件位置。
3. 做自己不依赖别人的工程骨架。遇到缺少接口时，先用固定数据继续，不原地等待。
4. 上传可以运行或可以校验的文件，同时说明“输入是什么、输出是什么、现在缺什么”。
5. 由数据的接收方实际读取 example；能读懂、能展示后，再共同确认字段并标记 `FROZEN-v1`。

“冻结”只是说后续代码按这一版字段写。发现必须改字段时，先同步修改 Schema、example 和相关测试，再通知受影响成员。

## A：Flutter APP 与整合

**通俗说法：**A 负责用户在手机上看见的 APP。第一天先把界面搭起来，让一份事先写好的报告能从首页打开。

**按顺序做：**

1. 建立 Flutter Android 工程，保证有首页和报告页。
2. 首页放“扫码、导入海报、粘贴链接、分享给触镜”四个入口。第一天可以先做入口外观，不要求它们真的完成扫描。
3. 定义 `analysis-input`：约定四种入口最后统一交给后续分析流程的数据长什么样。
4. 建立 `common.schema.json` 的最小版本，发给 B、C、D 确认公共字段。
5. 读取 D 给的固定 `analysis-report` example，在 APP 里展示风险等级、简短结论、承诺、实际行为、差异和证据编号。

**交付物：**`mobile/` 工程、首页、报告页、`analysis-input.schema.json`、`analysis-input.example.json`、`common.schema.json`，以及一张报告页截图或短录屏。

**当天怎样算完成：**APP 能启动；从首页能进入固定报告；B、C、D 知道以后该按什么格式给 A 传数据。

**当前仓库进度：**Flutter 工程骨架、首页和固定报告页面已经上传。现有固定报告是 A 为界面开发写的临时数据；D 的正式报告契约完成后，A 需要核对并接入正式 example。

## B：后端、账号与云端分析

**通俗说法：**B 负责公网“分析服务”。第一天先证明后端能启动、手机将来能知道它是否在线，并给 A、D 一份模拟的云端分析结果。

**按顺序做：**

1. 建立 `backend/` 和 FastAPI 最小工程。
2. 做 `/api/v1/health`：访问它能得到“服务正常”的 JSON。
3. 写一份模拟的云端证据，先包含任务状态、跳转结果、发现的域名或表单字段、证据编号。
4. 把这份结果整理成 `cloud-evidence.schema.json` 与 `cloud-evidence.example.json`。
5. 给 A 一份固定 JWT 和云端结果样例，给 D 一份可引用的 `Cxx` 证据。固定 JWT 只用于本地联调，不是真实账号系统。

**交付物：**`backend/` 工程骨架、可调用的健康检查、云端证据 Schema 和 example、最小运行说明。

**当天怎样算完成：**B 自己能启动后端并请求健康检查；A、D 可以读取 B 的固定云端证据，无需等待真正的 Playwright 沙箱。

## C：Android 本地安全能力

**通俗说法：**C 负责让手机“看懂链接和目标 APP”。第一天先用固定链接证明 Kotlin 模块的输入和输出长什么样。

**按顺序做：**

1. 在 `mobile/android/` 建立 Kotlin 安全模块的基本结构。
2. 准备普通 URL、自定义 Scheme 和 `intent://` 各一条固定样本。
3. 先解析能确定的字段，例如 Scheme、域名、包名、参数和 fallback；暂时无法确定的字段明确写 `null` 或空列表。
4. 整理 `local-evidence.schema.json` 与 `local-evidence.example.json`，本地证据编号使用 `Lxx`。
5. 给 A 一份固定的本地证据，让 A 能先做报告页面；给 D 同一份证据，供其写报告样例。

**交付物：**Kotlin 模块骨架、三类测试链接、本地证据 Schema 和 example、简单的输入输出说明。

**当天怎样算完成：**C 能用固定链接产出或手动准备一份符合约定格式的本地证据；A、D 能理解并使用它。

## D：AI、报告与测试材料

**通俗说法：**D 负责定义最终报告怎么说、每句结论引用哪条证据。第一天先给 A 一份能展示的报告，再完善 AI 提示词。

**按顺序做：**

1. **先给 A 一份最小固定报告**：风险等级、结论、差异、证据编号。这是第一天最早需要交接的东西。
2. 定义完整的 `analysis-report.schema.json` 和 `analysis-report.example.json`。
3. 补齐三份固定报告：高风险、低风险、证据不足。内容用虚构域名和脱敏数据。
4. 写 AI 提示词草案，要求结论只能引用真实证据编号；证据缺失时写“证据不足”。
5. 用 B、C 的证据 example 检查：报告里的 `Lxx`、`Cxx` 编号是否真的存在。

**交付物：**报告 Schema、至少三份固定报告、提示词草案、证据引用检查清单。

**当天怎样算完成：**A 可以展示 D 的正式报告 example；报告中的结论能找到对应证据，且“证据不足”有单独示例。

## 谁不完成会卡住谁

| 如果这个东西没交 | 会影响谁 | 具体卡在哪里 | 当天怎么继续 |
|---|---|---|---|
| D 的最小报告样例 | A | 无法用正式数据验收报告页 | A 先用现有临时报告继续做页面；D 优先交最小样例 |
| A 的公共字段与输入格式 | B、C、D | 正式 Schema 中的 ID、时间、输入字段可能各写各的 | B/C/D 先搭工程并写草稿 example；A 尽快发公共字段供确认 |
| B 的云端证据样例 | D，随后是 A | D 暂时无法校验 `Cxx` 引用；A 暂时无法做云端结果展示 | D 先用虚构云证据写报告；A 先展示本地报告 |
| C 的本地证据样例 | D，随后是 A | D 暂时无法校验 `Lxx` 引用；A 暂时无法接本地模块 | D 先用虚构本地证据写报告；A 先做固定报告界面 |
| A 的 Flutter 页面 | 第一天基本不卡 B、C、D | 当天无法完成“手机展示最终报告”的共同验收 | B 用命令行测 API；C 用原生测试入口；D 用 JSON 文件校验报告 |

这些依赖不会妨碍四个人同时开工。第一天只有最后的“正式报告在手机上展示”需要 A 和 D 对接；完整数据契约冻结需要四人共同确认。

## 卡住时，先做谁的任务

原则是：**先做自己任务里不依赖别人的部分；做完后优先帮助正在挡住联调的人检查样例，不随意改别人模块的代码。**

| 成员遇到卡点 | 先做自己的哪部分 | 如果已经做完，可以优先帮谁 |
|---|---|---|
| A 等 D 的正式报告 | 完成首页、报告页、输入格式；暂用临时报告 | 帮 D 检查报告字段是否都能在手机上显示 |
| A 等 B 或 C | 用固定 JSON 完成结果页和错误状态页面 | 帮 B/C 核对“给 APP 的输出”是否容易解析 |
| B 等 A 的公共字段 | 建 FastAPI、健康检查、云证据草稿 | 帮 A 检查公共 ID、时间和任务状态字段 |
| C 等 A 的公共字段或 Flutter 接口 | 建 Kotlin 骨架，用固定 URL/Intent 单独测试 | 帮 A 检查本地证据里包名、参数等字段是否够用 |
| D 等 B、C 的证据 | 先写报告 Schema、三份固定报告和提示词草案 | 帮 B/C 列出报告必须引用的证据字段 |

**优先级提醒：**A 的公共字段、D 的最小报告应尽早发出；B、C 的证据样例随后交给 D；最后 A 用正式 example 展示报告。每个人都可以先做自己的工程骨架，不必等这条交接链全部完成。

## 交接时发给队友什么

不要只说“我做好了”。每次交接附上下面四句话即可：

```text
我完成了：<文件路径或接口>
你可以这样试：<一条运行命令或一个输入样例>
正常会得到：<输出文件或截图>
目前还缺：<未实现内容；没有就写“无”>
```

交接状态建议用 `TODO → DOING → READY → DONE`；确实等不到前置材料时标记 `BLOCKED`，同时写明自己正在做的替代任务。`READY` 表示“我交出来了”，`DONE` 表示“下游已经读取并确认能用”。

## 第一天结束前一起验收

- [ ] A、B、C、D 都把自己的工程骨架或文档提交到同一个 TapLens 仓库；
- [ ] 四份业务 Schema 和对应 example 已存在，公共字段已由四人确认；
- [ ] Schema、example 与多案例 fixture 的用途没有混淆；
- [ ] D 的报告 example 能引用 B/C 提供的证据编号；
- [ ] A 能在手机 APP 中展示一份固定报告；
- [ ] 所有人知道第二天从哪个文件和哪项任务继续；
- [ ] 确认无真实 API Key、密码、个人信息和服务器密钥进入 Git。

若最后两项联调暂时未完成，直接标出具体卡点和负责人，其他人继续开发各自模块。四份契约只有通过产出方生成、接收方读取和共同审核后，才标记为 `FROZEN-v1`。
